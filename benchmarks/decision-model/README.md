# Decision-model benchmark (Phase 13)

Which small local model decides best when the question is a
candidate-conditioned Choice — pick one option id from a fixed list — and
how fast, how calibrated, and how deterministically does it do it? This is
the measured answer to "can a general small LLM replace a trained decision
model in the escalation ladder?" before any weights are trained.

## What is compared

Every arm answers the same 120 committed questions (`suite/suite.json`) and
is scored on top-1 candidate-id accuracy, ECE of its winner probability,
latency, and run-twice determinism:

| arm | runner | mechanism |
|---|---|---|
| `engine_builtin_lexical` | `run_engine.py` | OpenCodifier's own engine (`opencodifier serve`, builtin lexical pipeline) — the zero-ML baseline every model must beat to earn its latency |
| `embedding_zero_shot` | `run_embed.py` | MiniLM ONNX cosine + softmax — the "embedding similarity" layer of the ladder |
| `llama_decision` | `run_llama.py` | llama.cpp `parallel-decision` branch (`POST /v1/decision`): every candidate id scored as a token path forked from one cached prefix; tree mode returns the exact constrained distribution, nothing is sampled |
| `llama_decision` chat baseline | `run_llama.py --skip-chat` opt-out | the same questions written as JSON by ordinary token-by-token chat completion at temperature 0 — what the decision arm replaces |

The decision-arm design and the latency targets follow the operator-supplied
reference (`docs/References/Can Your GPU Hit Jev's Milliseconds Mark.txt`)
and the branch it documents
([thecodacus/llama.cpp `parallel-decision`](https://github.com/thecodacus/llama.cpp/tree/parallel-decision)):
options that differ in their first scored token need no letter-coding; the
instructions + schema prefix is prefilled once and cached; batched contexts
decide in one forward pass. The three suite classes deliberately span what
the reference found to be the task-dependent floor: attribute checking
(`metadata_match`), paraphrase routing (`lexical_semantic`), and the
relational/compositional cases where small models collapse
(`relational_compositional`).

## Suite

`suite/suite.json` is generated by `suite/generate_suite.py` and committed
byte-locked (seed 20260926; rerunning the generator reproduces the exact
bytes). Ground truth holds by construction — each item is a Choice question
in the canonical IR shape with exactly one correct candidate id. It is
benchmark fixture data, not product data.

## Running

Write run outputs OUTSIDE the repository tree — raw run JSONs are
measurement data (walls of floats and model outputs), not source; the repo
commits only the merged evidence (see Results below):

```bash
RUNS=/nas/Temp/work/oc-model-eval/runs   # out-of-tree

# 1. engine baseline (no ML, no models needed)
python3 runner/run_engine.py --binary target/release/opencodifier \
    --out "$RUNS/engine__builtin-lexical.json"

# 2. embedding arm (models/minilm/{model.onnx,tokenizer.json})
python3 runner/run_embed.py --model-dir /path/to/minilm \
    --out "$RUNS/embed__minilm.json"

# 3. decision arm per GGUF model (downloads are operator-supplied; the
#    runner records each file's SHA-256 into the results)
python3 runner/run_llama.py --llama-dir /path/to/llama.cpp \
    --models-dir /path/to/models --model qwen2.5-0.5b-instruct-q4_k_m.gguf \
    --out "$RUNS/llama__qwen2.5-0.5b.json"

# 4. merge everything, then copy summary.md + models.manifest.json in-tree
python3 runner/summarize.py --results-dir "$RUNS"
```

Model weights never enter the repository; `models.manifest.json` (written by
`summarize.py`) pins the SHA-256 of every artifact a result was produced
with, per the model-manifest practice in `docs/DECISIONS.md` (D14).

## Determinism

The decision arm samples nothing: tree mode scores every divergence node of
the candidate token trie, so probabilities are exact and repeatable. The
runner replays the whole suite a second time and records
`determinism.predictions_match` plus the maximum probability delta; a `NO`
in the summary table is a finding, not a rounding note.

## Results

`results/` commits the merged evidence only — `summary.md` (the
comparison table the Phase 13 record in `docs/PLAN.md` and the pick in
`docs/DECISIONS.md` D16 rest on) and `models.manifest.json` (SHA-256 of
every model and embedder used). Raw per-run JSONs stay out of the repo
tree: they are regenerable from the pinned inputs — the suite is
byte-locked, every arm replays twice with predictions matching
(`determinism.predictions_match` in each run file), and the artifacts
are pinned by the manifest — and data files consisting of thousands of
measurement floats are content the scanner gate should never have to
triage.
